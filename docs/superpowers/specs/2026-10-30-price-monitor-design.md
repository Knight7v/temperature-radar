# 竞品到手价监控 开发规格（京东 · 格力/海尔）

- 日期：2026-10-30（v3，数据源定为纯前台抓取，明确排除联盟 API）
- 状态：P0 进行中。已落地：迁移 `0019_price_monitor.sql`、判价核心 `lib/price/evaluate.js`、展示整形 `lib/price/view.js`、数据访问 `lib/price/store.js`、接口 `handlers/price.js`（页面已切真实数据）。待做：采集器、企微推送、链接批量导入。
- 集成位置：观星台工作台新增一级菜单「价格监控」，页面 `price.html`。
- 使用者：副总/运营（看告警、处理）、管理员（配阈值、维护链接）。

## 1. 目标与范围

每天 2 次采集 **200–300 条竞品链接 + 60–120 条我方链接**的到手价；当某机型的**竞品最低可得价低于我方基准价**时，落库并在企业微信群通知；页面可按机型查当日命中、价差与历史。

核心结构：**以「机型」为枢纽**，一个机型下挂多个我方链接（多店在售）和多个竞品链接（多家竞店在售）。判价在机型层聚合，避免同一台机器被 5 家竞店各报一次。

**不做**：自动调价、代下单、全站比价、秒杀级实时（受采样频率限制，见 §4.7）。

成功标准：宁可漏报不可假报——采不到就显示"数据缺失"，绝不用上一次价格冒充本次；同一机型同一天最多一条业务告警。

## 2. 已确认的业务决定

| 项目 | 决定 |
| --- | --- |
| 平台 | 京东（POP + 自营） |
| 竞店 | 格力 5 家 + 海尔 5 家 = 10 家 |
| 监控规模 | **每个竞店 20–30 个重点机型**：格力 5×20–30 + 海尔 5×20–30 = **竞品链接 200–300 条** |
| 我方链接 | 同批机型在我方京东店的在售链接，预计 60–120 条（按实际在售） |
| 我方价格来源 | 抓取（带登录态，含 PLUS 价与可领券） |
| 到手价口径 | **最低可得价为主告警线**，基础价作参考列，新客价单列提示 |
| 告警阈值 | `max(3 元, 0.3%)`，满足任一即报（2026-10-30 由 1 元/0.5% 上调） |
| 采样时点 | 10:00 全量 + 20:00 重点机型（Asia/Shanghai） |
| 采集载体 | 用户本机 Mac 定时跑（零成本，需开机） |
| 推送方式 | **日常只发一条汇总；明显击穿（≥5 元或 ≥2.5%）才单独弹一条** |

## 3. 口径定义（本规格最核心部分）

### 3.1 三种价格，含义不能混

| 代号 | 名称 | 构成 | 用途 |
| --- | --- | --- | --- |
| P0 | 基础价 | 未登录、非会员、不领券，页面直接显示的商品价（京东价或直降后价） | 参考列、页面展示、横向可比 |
| **P1** | **最低可得价（老客）** | 登录态（PLUS）＋ 可领店铺券 ＋ 可领平台券 ＋ 满足门槛的满减 ＋ PLUS 专享 ＋ 页面明示支付立减；**不含运费** | **主告警线** |
| P2 | 新客价 | P1 再叠加新人券 / 首单礼金 | 仅作"新客击穿"提示，**不进主告警** |

> **必须审阅的默认值**：不把新客价并进主口径。京东几乎每个链接都有新人立减（常见 30–100 元），若并入，200–300 条链接会天天全线告警，告警立即失效。故 P2 单列。

恒等式 `P2 ≤ P1 ≤ P0`；违反即判为解析异常，该条不参与告警。

### 3.2 机型层聚合

```
机型基准价   = min(该机型下全部我方链接的 P1)      // 多店在售取最低，避免自家店互相"打自己"
机型竞品价   = min(该机型下全部竞品链接的 P1)
```

我方机型基准价缺失（机型未在我方任何店在售、或全部采集失败）→ 该机型不判价，进"待处理"清单。

若同一机型在我方多店价差 > 5%，额外标"内部价格冲突"提示运营——这不属于竞品问题，不能混进竞品告警。

### 3.3 价差与触发

```
gap      = 机型基准价 − 机型竞品价        // 正数 = 竞品更便宜
gap_rate = gap / 机型基准价
触发     = (gap ≥ 3 元) 或 (gap_rate ≥ 0.3%)   // 满足任一即报
```

阈值已于 2026-10-30 由 `1 元 / 0.5%` 上调为 `3 元 / 0.3%`，目的是滤掉 1–2 元的凑单调价。

对空调这种几千元的商品，**金额门槛通常先触发**：3000 元的 0.3% 是 9 元，差 5 元时只有金额门槛起作用；比例门槛主要在 1000 元以下的小家电上才会先触发。因此"满足任一"实际近似等于"差 3 元就报"，噪声控制仍**主要靠** §6.2 的机型聚合与状态机，不要指望阈值。

### 3.4 置信度

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| high | 价格构成全部来自页面且可计算 | 正常告警 |
| medium | 部分券需登录/需点击领取，已取得 | 正常告警 |
| low | 存在只在结算页出现的优惠，未取得 | **仍告警**，标注"置信度低，可能更低" |
| invalid | 被风控/验证码/改版 | 不算价格，记采集失败 |

取不到券会让计算价**偏高**，只会漏报不会假报，因此 low 可放行。

### 3.5 明确不含

运费、地区差异、以旧换新/政府补贴、采样时点之外的限时秒杀、非 PLUS 档的会员阶梯价。

## 4. 采集设计

### 4.0 数据源决策：只抓前台，不用京东联盟 API（2026-10-30 用户拍板）

**结论：排除联盟 API。全部价格来自京东前台页面（带登录态抓取）。**

理由（这是业务判断，不是技术偏好，后续不得再改回去）：

1. **联盟价是"推广者视角"，不是"顾客视角"。** 联盟接口返回的是带佣金链接的推广价，包含**联盟专属券**——这类券前台顾客看不到、也领不到。拿它当监控基准，会算出顾客根本拿不到的低价，变成天天假报。
2. **前台大量优惠联盟接口不返回。** PLUS 会员价、平台券、新人券、运费券、部分店铺券只在登录态下的前台可见。联盟接口给不到，算出来的价会系统性偏高，导致漏报。
3. **两个口径的差额无法解释。** 一旦出现"联盟说 2999、前台要 3099"，运营无法判断是竞店调价还是口径差异，比价结论直接失效。
4. 顺带的风险：联盟接口对自营与部分 POP 商品覆盖不全，覆盖率本身也撑不起 200–300 条的监控面。

**因此本规格的唯一定义：价格 = 顾客在京东前台、用我们的登录态（PLUS）实际能看到的价。**
这意味着采集器必须处理：登录态维持、券的领取（可能弹验证）、PLUS 价与普通价的区分、以及"某些优惠只在结算页出现"的不确定性（对应 §3.4 的 low 置信度）。

代价（已知并接受）：维护成本高于调 API；京东改版要跟着改解析；登录态过期要人工扫码。

#### 4.0.1 通道实测结论（2026-11-02 更新，这节决定用哪条路）

| 通道 | 结果 | 结论 |
| --- | --- | --- |
| `item.jd.com`（PC 详情页）+ 无头浏览器 | 返回「PC频控页」，连未登录也一样 | ❌ |
| `item.jd.com` + 有头浏览器（真实窗口 + 登录态） | 302 到 `cfe.m.jd.com/.../risk_handler/` 「京东验证」 | ❌ 需要人工过验证码，自动化不可用 |
| `item.m.jd.com`（移动详情页）纯 HTTP + 登录态 | ✅ 服务端直出，标题/店铺/价格一次拿全，1~3 秒 | ✅ **当前唯一可用** |
| `item.m.jd.com` 浏览器打开 | 和纯 HTTP 一样会被 302 到 `trade.m.jd.com/common/limit.html` | ❌ 换浏览器不解决问题 |

三个必须知道的坑：

1. **频控是按 IP 计的，与登录态无关。** 2026-10-31 当天密集测试后，整个 IP 进入"罚站"状态：每一条请求都要先吃一次 302、等 3~4 分钟冷却才成功，折合 3.3 分钟/条。**任何通道、任何 UA、任何登录态都一样**，换浏览器无效。停两天后自动恢复（11-02 早上连发 5 条没有再限流）。
   → 对策：间隔拉到 25~45 秒；被限流长退避一次；整轮遇连续限流就中止，**绝不硬撞**（撞得越多罚得越久）。
2. **券后价拿不到。** 券区块（`#summary-quan`）只在 PC 页有，而 PC 页被「京东验证」挡住。移动页只有 `jdPrice`（真实价）和 `price`（划线价），没有 coupon / plusPrice 字段。
   → 结论：**主口径暂时只能是「页面价」**（含国家补贴，多数机型这句话就等于到手价）。页面 `notes` 会写明"券后更低时会漏报，不会假报"。
3. **登录态"假有效"。** `thor` cookie 会散落在 `yiyaojd.com` / `jdcloud.com` / `jingxi.com` 等几十个子域，有效期到 2027 年；但主域 `jd.com` 上的那个可能已经没了。按"cookie 名出现过"判断会得出"已登录"，实际价格全是打码的。
   → 已修：`session.hasAuthCookies()` 现在要求**主域 `jd.com`** 上凑齐 cookie 才算登录。

### 4.1 载量与时长（关键约束）

| 项 | 数值 |
| --- | --- |
| 每轮链接数 | 一期 60 条（每店 6 个重点机型）；跑顺后再扩 |
| 单条间隔 | 25–45 秒随机（频控惩罚下重，宁慢勿废） |
| 单轮耗时 | 约 25–45 分钟 |
| 硬超时 | 60 分钟，超时记"部分完成" |
| 日请求量 | 约 120 次（两轮） |

> 20:00 只跑重点机型，是为了让大促当晚的结果在 21:00 前出来；若全量跑，跑完已 21:00–22:00，失去"当晚发现当晚处理"的意义。
> ⚠️ 原计划 260–420 条经实测不可行（单条约 3.3 分钟 → 一轮十几小时），已按用户 2026-10-31 拍板降到 60 条起步。

### 4.2 载体与调度

- 脚本：`scripts/price-crawler.js`（Node + Playwright，复用项目已装 `@playwright/test` 的 Chromium）。
- 调度：macOS `launchd` 两个时点（10:00、20:00，Asia/Shanghai），日志 `data/price-crawler.log`。
- **休眠补采**：launchd 错过任务会在唤醒后补跑；脚本启动先查 `price_runs` 当天该 slot 是否成功，未成功则补采一次并标 `catchup=true`。
- 顺序：先我方链接（登录态，取 P1/P0），再竞品链接（**同一登录态**，取 P1/P0/P2）。
- 竞品也必须带登录态：PLUS 价是**账号权益**，与在哪家店无关，无痕会话只能拿到未登录价，等于放弃主告警线。代价是同一账号每天要访问 260–420 条链接，账号风控风险上升 → 必须低频、间隔随机、固定本机 IP，且**只用一个专用账号**，禁止使用高管本人常用账号（一旦被限制影响日常购物）。

### 4.3 登录态

- 我方价格需登录（PLUS 价与可领券）。会话 cookie 存本地 `data/price-session.json`，**不入库、不进 git、不写日志**。
- 每轮开始先校验会话有效性。
- 失效 → 立即发运维告警"京东登录已失效，请重新扫码"，本轮我方链接全部记 `failed`，不判价、不产生业务告警。
- 严禁在代码或数据库存账号密码；扫码一次可持续数天至数周。

### 4.4 频控与熔断

- 单条失败重试 1 次（间隔 30 秒）。
- 连续 10 条失败 → 判定疑似风控，本轮立即停止，记 `blocked`，发运维告警。
- 单轮验证码/404 比例 > 30% → 记 `degraded`，本轮不判价。

### 4.5 数据完整性铁律

- 采不到即 `status='failed'`，该链接本轮不参与聚合，页面显示"今日数据缺失"。
- **严禁用上一次价格代替本次**；页面必须能区分"今日已采 / 今日缺失 / 上次采集于 X"。
- 机型下所有竞品链接都失败时，该机型标"竞品数据缺失"，不能用部分链接的结果下"竞品更贵"的结论。

### 4.6 合规边界

只读公开商品页；不模拟下单、不绕过验证码、不破解风控；每链接 ≤ 2 次/天。若被平台限制，停止采集并切人工导入兜底（§6.5）。

### 4.7 已知局限（需让业务方知情）

每天 2 次只能覆盖常态价与持续数小时的促销。整点秒杀、1 小时限时券大概率抓不到。20:00 轮对准晚 8 点大促，618/双 11 建议临时加到 4 次（配置项）。

## 5. 数据模型

迁移 `lib/db/migrations/0019_price_monitor.sql`，配套 `lib/price/schema.js` 的 `ensurePriceSchema()`（读迁移执行一次，失败重置重试），与现有模块一致。所有表带 `tenant_id`。

| 表 | 关键字段 |
| --- | --- |
| `price_models` | id, tenant_id, brand(gree/haier), model_code（归一后，租户内唯一）, series, capacity, title, priority(1重点/2普通), enabled |
| `price_links` | id, tenant_id, model_id, side(own/competitor), shop_name, url, item_id, list_title, raw_model（页面抓到的型号原文）, confirmed_by, confirmed_at, enabled, last_status |
| `price_observations` | id, tenant_id, link_id, model_id, observed_at, base_price, best_price, new_user_price, price_detail jsonb, confidence, status(ok/failed/blocked/degraded), note |
| `price_alerts` | id, tenant_id, model_id, competitor_link_id, first_seen_at, last_seen_at, gap_amount, gap_rate, my_price, comp_price, comp_shop, other_lower_count, confidence, status(open/recovered/ignored), notified_at |
| `price_config` | id, tenant_id, threshold_amount(1), threshold_rate(0.005), schedule jsonb, webhook_enc, notify_mode, enabled, updated_at |
| `price_runs` | id, tenant_id, run_at, slot(full/focus/manual), catchup, total, ok, failed, blocked, status, duration_ms, error |

索引：`price_links(tenant_id, model_id, side)`、`price_observations(tenant_id, link_id, observed_at desc)`、`price_alerts(tenant_id, status, first_seen_at desc)`。

**我方与竞品用同一张 `price_links` 表，靠 `side` 区分**：300+ 条链接用一张表便于批量导入、批量确认和统一切换启停。

### 5.1 300 条链接怎么进来（P0 必须有，否则无法上线）

手工录入 300 条不现实。流程：

1. 运营批量粘贴 URL（一行一个，支持从京东商品页直接复制）。
2. 系统抓 `item_id`，读取商品标题，用 `lib/product/groups.js` 的 `normalizeModel()` 提型号。
3. 按型号自动归组到 `price_models`；型号提不出的进"待确认机型"。
4. 人工只做**确认/纠正**（预计 200–300 条 20–30 分钟），确认后才参与判价（`confirmed_by` 非空）。
5. 型号归一必须可追溯：同时保留 `raw_model` 原始文本，页面展示"系统识别为 X / 原文 Y"，识别错可一键改。

## 6. 判价与告警

### 6.1 每轮流程

1. 采集 → 写 `price_observations` + `price_runs`。
2. 按机型聚合：机型基准价（我方 P1 最低）、机型竞品价（竞品 P1 最低）、次低价竞店与"另有 N 家更低"。
3. 命中判定（§3.3），仅 `ok` 状态参与。
4. 去重与状态机（§6.2）→ 命中写 `price_alerts`。
5. 发企微（汇总为主，明显击穿才单条）。

### 6.2 去重与状态机（噪声控制的核心）

- **按机型聚合，不按链接**：同一机型 5 家竞店都更便宜，只报 1 条（列最低那家 + "另有 4 家更低"）。
- 同一机型每天最多 1 条业务告警。
- 状态机：`open` → 竞品回升至不满足阈值 → `recovered`（发一条"已回升"）→ 再跌破重新 `open` 并再报。
- 持续下探：已 `open` 且较上次再降 ≥ 10 元，可选发"继续下探"（默认关闭）。

### 6.3 推送模式（已确认）

- **汇总必发**：每轮结束发一条，含命中机型数、最大价差、缺失数、我方登录状态。
- **单条实时**：仅当 `gap ≥ 5 元 或 gap_rate ≥ 2.5%` 时单独推一条，其余只进汇总。
- 每机型每天最多 1 条，避免 200–300 条链接把群刷爆。

### 6.4 运维告警（独立格式，不与业务告警混）

京东登录失效、连续失败熔断、单轮缺失率 > 30%、今日两次均未采集。

### 6.5 人工兜底

采集失败当天，允许在页面粘贴关键机型竞品价（`manual` 标记、来源标"人工"），保证告警不断档；人工数据不覆盖采集数据，两者并列展示。

## 8. 页面 `price.html`

1. **今日概览**：命中机型数、最大价差、缺失链接数、我方登录状态、最近采集时间（未采集红字）。
2. **命中列表（按机型）**：机型｜我方价（最低）｜竞品价（最低）｜价差｜更低竞店数｜置信度｜首次发现｜状态｜操作（忽略/已处理）。
3. **机型下钻**：某机型的全部我方/竞品链接、各自价格、采集状态。
4. **缺失清单**：采不到的链接与原因（风控/改版/下架），可手动补价。
5. **链接管理**：批量粘贴导入、自动归组结果、确认/纠正、启停。
6. **历史**：单机型价格趋势（我方 vs 最低竞品，自托管 Chart.js）。
7. **配置**：阈值、时点、webhook、推送开关。

导航挂 `js/workbench-shell.js` 的 `MODULES` 新增一级菜单「价格监控」，admin/operator 可操作，viewer 只读。

## 11. 验收标准

1. 全量轮 260–420 条链接成功率 ≥ 90%，失败逐条有原因；单轮耗时 ≤ 60 分钟。
2. 恒等式 `P2 ≤ P1 ≤ P0` 违反记为解析异常且不告警。
3. 机型聚合：同一机型 5 家竞店都更低 → 只 1 条告警，`other_lower_count=4`。
4. 阈值：3000 元机型差 0.9 元不报；差 1.0 元报；差 0.4%（12 元）报。
5. 去重：同机型当天只推 1 次；回升后发"已回升"；再跌破重新告警。
6. 失败不伪装：某链接失败 → 显示缺失、不参与聚合、不用旧价；机型下全部竞品失败 → 标"竞品数据缺失"。
7. 登录失效 → 运维告警 + 我方链接全标缺失，不产生业务告警。
8. 连续 10 条失败 → 本轮停止并告警（`blocked`）。
9. 20:00 重点轮只跑 `priority=1`，耗时 ≤ 40 分钟，且不影响 10:00 全量数据。
10. 休眠补采：10:00 未跑，11:30 唤醒后补跑一次，`price_runs.catchup=true`。
11. 批量导入 300 条 URL：自动归组后人工确认可在 30 分钟内完成，识别错的能改并留痕。
12. 权限与租户：viewer 无法改配置；跨租户链接/告警不可见。
13. 页面、企微、导出三处数字同源（同一次 `price_runs` 结果）。

## 13. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |

## 14. 已确认结论

1. 10 家为**竞争对手店铺**；每个竞店 20–30 个重点机型，合计竞品链接 200–300 条。
2. 推送方式：日常一条汇总，明显击穿（≥5 元或 ≥2.5%）才单独弹。
3. 新客价单列，不进主告警口径（避免新人立减导致全线告警）。
4. **数据源：只抓京东前台（带登录态），不接京东联盟 API。** 联盟价含联盟专属券、缺 PLUS/平台券，与顾客到手价是两个口径（详见 §4.0）。
5. 不注册京东联盟账号；因此 P0 起采集器即为唯一数据入口，人工补价仅作兜底。
6. 阈值 `max(3 元, 0.3%)`，满足任一即报（原 1 元/0.5% 已上调，滤掉 1–2 元的凑单噪声）；明显击穿仍按 ≥5 元或 ≥2.5% 单独推送。

**仅剩一个事实待补**：我方这 200–300 个机型在你自己店里实际有多少条在售链接（预计 60–120 条）。这个数字只影响首轮耗时，不影响设计，可在实施时用实际数据填。

## 15. 链接管理（2026-11-02 用户要求补充）

问题：导入页只有「粘贴 → 解析」，入库后**看不到自己挂了哪些链接**，只能靠「今日对比」里那几行命中判断，没采到的、刚挂上的、被停用的全都不可见。

现结构：`链接管理` 拆成两个子 TAB。

| 子 TAB | 做什么 | 关键约束 |
| --- | --- | --- |
| 导入链接 | 粘贴 → 选归属商品（可选已有 / 当场新建：品牌+系列+匹数）→ 选阵营（竞品/我方）→ 预览（将新增 / 已存在 / 无效）→ 确认导入 | **不读京东页面**（只写关系，标题店铺留给第一次采集补齐），所以一次贴 300 条也不吃频控；同一批批内去重；已在别的机型下的默认**不挪**，要挪必须显式勾选 |
| 查看链接 | 按商品（机型）分组列出全部链接，含未采集、已停用；点商品编号新窗口打开京东页；可停用/启用/删除；支持搜索与品牌、阵营、状态筛选 | 只显示「最近一次成功到手价」，不冒充今日价；已停用的保留历史；删除会级联删快照，必须二次确认 |

接口：`GET /api/price/links`（清单）、`POST /api/price/links`（`op=import|status|side|remove`）。纯函数在 `lib/price/links.js`（解析/归一/去重/机型键），整形在 `view.buildLinkGroups`，单测 `tests/price-links.test.js`。

**同日修掉的隐藏 bug**：`js/price.js` 的 `api(path)` 只收一个参数、把第二个 `init` 丢了，导致所有 POST（保存设置、忽略告警、立即采集、导入链接）实际都按 GET 发出——页面还显示成功。配置改完刷新就还原、忽略点了没反应，根因都是它。
