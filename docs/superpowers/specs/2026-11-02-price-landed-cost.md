# 比价助手 · 到手价口径改造方案（已实施）

- 日期：2026-11-02
- 状态：**已按用户答复实施完成**
- 关联：`docs/superpowers/specs/2026-10-30-price-monitor-design.md`（原比价方案）
- 起因：现有采集只读「标价/补贴价」，漏掉券和国补，导致系统性漏报（示例机型差 719.7 元）

---

## 1. 口径定义（用户 2026-11-02 拍板）

### 1.1 公式

```
券后价   = 标价 − 促销直减
国补抵扣 = min(券后价 × 国补比例, 国补上限)          // 按券后价算，不是按标价
到手价   = 券后价 − 国补抵扣
```

### 1.2 算例校验（必须逐位对上，作为验收基准）

| 项 | 值 | 来源 |
| --- | --- | --- |
| 标价（补贴价） | ¥3098 | 页面 `jdPrice` |
| 促销直减（单品满1件减300） | ¥300 | 页面促销 JSON（`promoType:26 / unitBuyMore`） |
| 券后价 | ¥2798 | 计算 |
| 国补比例 / 上限 | 15% / ¥1500 | 页面文案「国家补贴京东支付享15%，最高可减1500元」 |
| 国补抵扣 | ¥419.7 | 2798 × 15% |
| **到手价** | **¥2378.3** | 与京东 App「国补领后价」一致 |

### 1.3 口径边界（已确认）

| 项 | 结论 |
| --- | --- |
| 以旧换新额外省 260 | **不算**进到手价，单独记一列，只在页面提示 |
| 需领券 / 需实名领国补才成立的价 | **算**，但必须标注「需领券」「需实名」 |
| PLUS 价 / 新客立减 | **不进**主口径，单独展示 |
| 国补比例、上限 | 当期可配，不写死 15%/1500 |

## 2. 数据来源实测结论（2026-11-02 11:00 本机实测）

| 结论 | 证据 | 影响 |
| --- | --- | --- |
| 券信息**在纯 HTTP 返回的页面源码里** | 促销 JSON 片段：`"97":"满1件减300元"..."promoType":26,"ori":"1"`（`PROMO_TYPE_unitBuyMore`） | **不需要浏览器**，沿用现有 HTTP 通道即可，1–3 秒/条 |
| 国补**不在页面上**（页面只有「15%、最高1500」的规则文案） | 全文检索「国补」「2378」「419」均无金额 | 国补必须**算**，不能抓 |
| 浏览器渲染也能读到券（正文含「优惠 单品满1件减300元」） | headless Chrome + 登录态，6.1s/条 | 作为 HTTP 的降级通道 |
| 京东**按 IP 限流**，无差别打击 HTTP 与浏览器 | 实测触发 `trade.m.jd.com/common/limit.html?module=detail_m1` | 节流是硬约束，见 §6 |

> ⚠️ 结论：用户选的「B 路线（拦截页面数据）」实际形态是——**HTTP 拿页面源码里的促销 JSON**，比浏览器拦截更轻。顺序调整为：HTTP 解析 → 失败降级浏览器 → 再失败标缺失。

## 3. 字段改造

`price_observations` 现有 `p0（标价）/ p1 / p2`，含义与新口径冲突，按下面重建（新列 + 旧列只读保留，页面不再展示旧列）：

| 新列 | 含义 | 类型 |
| --- | --- | --- |
| `listed_price` | 标价（页面 `jdPrice`） | numeric(12,2) |
| `promo_amount` | 促销直减合计（券/满减，可叠加的） | numeric(12,2) |
| `after_promo_price` | 券后价 | numeric(12,2) |
| `subsidy_rate` | 本次生效的国补比例（0.15 / 0.20 / 0） | numeric(5,4) |
| `subsidy_amount` | 国补抵扣 | numeric(12,2) |
| `landed_price` | **到手价（主口径）** | numeric(12,2) |
| `promo_text` | 券原文（如「单品满1件减300元」），便于人工复核 | text |
| `subsidy_flag` | `yes` / `no` / `unknown`（页面是否有国补标识） | text |
| `price_confidence` | `high` / `low`（券缺失、国补未知 → low） | text |

机型层聚合、告警判定、企微文案、页面展示**统一改读到手价**；标价仅作为下钻明细展示（用户答 8：不保留标价差告警）。

## 4. 抓取流程

```
① HTTP 取 item.m.jd.com 页面源码
    └ 命中促销 JSON → 解析 promoAmount 列表，按门槛过滤可生效项
    └ 命中 limit.html / 登录墙 → 标记 rate_limited / need_login，走退避
② 若 ① 拿不到 promo（页面结构变了 / 限流）
    └ 降级：headless Chrome + 登录态渲染，读「优惠」行文本（6s/条）
③ 若 ② 也失败 → 该条记 low 置信，到手价留空（**不许用标价冒充到手价**）
④ 国补：查 SKU 级规则（默认 15%/1500），算 min(券后 × 比例, 上限)
⑤ 入库 → 判价 → 推送
```

### 4.1 券的三条铁律

1. **必须过门槛**：`满2000减300` 在券后价 < 2000 时不生效，不能减。
2. **只认可叠加项**：页面「优惠」行里并列的直减项相加；PLUS 价、新客价、以旧换新不并入。
3. **原文必须存**：`promo_text` 保留券文案，人工能对账；解析不出金额 → 记 low，不猜。

### 4.2 国补规则

- 默认：比例 15%，上限 ¥1500（当前页面文案）
- 支持按 品类 / 品牌 / SKU 覆盖（配置表 `price_subsidy_rules`，无命中则用默认）
- 页面无国补标识（`subsidy_flag=no/unknown`）→ 按无补贴算，该条标 `low`（用户答 6）

## 6. 节流与规模

| 项 | 现状（实测） | 改造后 |
| --- | --- | --- |
| 单条耗时 | HTTP 0.3–3s；浏览器 5–7s | 主要走 HTTP |
| 单条间隔 | 12–22s 随机 | 维持（实测 4 条 1'45"、零限流） |
| 60 条一轮 | 约 26 分钟 | 约 20–26 分钟（含偶发退避） |
| 触发限流 | `trade.m.jd.com/common/limit.html` | 退避 3 分钟重试 1 次，连续 2 次整轮中止 |
| 每日轮次 | 10:00 全量 + 20:00 重点 | 不变 |

> 实测提醒：连续调试会把这个 IP 打进「惩罚状态」（曾需停两天恢复）。**改造期间不要高强度反复试抓**。

## 8. 三个待定项已确认（2026-11-02 用户拍板）

**① 多个促销同时存在时怎么叠？→ 保守**
只加页面「优惠」行里并列展示、可叠加的直减项，不推断互斥规则；门槛按「前面券减完后的金额」判断（比京东实际更严）。
代价：偶尔少减 → 到手价偏高 → **只会漏报，不会报一个顾客拿不到的价**。

**② 限时券怎么处理？→ 抓取时刻有效就算**
把券的失效时间一并写入 `promo_expire_at`（取最早过期的那张）；过期后下一轮自然消失，不额外告警。

**③ 国补是否所有机型一致？→ 统一 15% / 上限 1500**
写进 `price_settings.subsidy_rate` / `subsidy_cap`，页面可改。国补按**券后价**计算，不按标价。
