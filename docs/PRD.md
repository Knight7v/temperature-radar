## 1. 背景与问题

### 1.1 项目是什么
一套"天气 → ADI 销售热度指数 → 可视化看板 → 企微推送"的**空调销售决策支持系统**。核心管线已可用且有测试覆盖:抓取和风天气 7 天预报 → 计算 ADI 分级(爆热/热/待热/…)→ 渲染中国热力图、城市榜、大区统计、每日简报 → 每日定时向企业微信推送"高温重点关注"与"升温预报"(达标才推)。

### 1.2 定位转变
项目此前以"单组织内部工具"的形态开发。2026-08-06 确认最终定位为**对外多租户 SaaS**(卖给多家空调厂商/经销商)。这一转变不是新增一个功能,而是要求**整体骨架从单租户重构为多租户**。

### 1.3 为什么要做
- **行业痛点**:空调销售高度依赖天气,但厂商/经销商普遍缺乏"把天气信号转化为铺货、促销、安装产能调度决策"的工具,凭经验调货导致热浪期缺货或错配。
- **机会**:用结构化的 ADI 模型 + 每个客户自己的市场/销量数据,提供"哪热、热多久、能卖多少、该把货和安装队投到哪"的决策支持。

测试:`node --test tests/*.test.js` 当前 76/76 通过,覆盖天气解析、ADI/降水逻辑、企微消息、主题、Vercel 配置。

### 2.2 单租户写死:四个硬伤 🔴
当前代码**从结构上就是单租户的**——这是 SaaS 化的最大障碍:

| 单租户写死处 | 代码位置 | SaaS 要求 |
|---|---|---|
| 城市集为硬编码数组(约 40 个省会/主要城市,仅有 lat/lng/province/region) | `CITIES_CONFIG`(`js/adi-core.js:725`) | 每租户自定义销售区域/城市集,并携带市场属性 |
| 模型阈值与权重为全局常量 | `ADI_CONFIG`(`js/adi-core.js:15`) | 每租户可标定(品类、区域不同,"爆热"销量含义不同) |
| 推送目标为单个环境变量 | `WECOM_BOT_WEBHOOK`(`api/cron-push.js`) | 每租户独立 webhook + 推送计划 + 门槛 |
| 无租户/鉴权概念,曾用 fs JSON 单命名空间做"数据库" | (已删 `data/*.json`、`lib/helpers.js`) | 租户隔离的真实数据库 + 真鉴权 |

**唯一可保持平台级共享的层是天气抓取**(`lib/qweather.js` + `api/weather.js`)——QWeather key 为平台资产,数据对所有租户通用。其上一切均需租户化。

### 2.3 已下线的商业化层(2026-08-06)
分支 `remove-commercialization-layer` 删除了:`js/auth.js`、`js/payment.js`、`js/ads.js`、`js/test-mode.js`、`api/auth/*`、`api/payment/*`、`lib/helpers.js`、`data/products.json`、`payment-demo.html`。

**删除原因(均为 SaaS 不可接受的硬伤)**:
- 鉴权 handler 调用的辅助函数无 import → 运行时 `ReferenceError`;
- `generateJWT`/`verifyJWT` 为假签名(字面量 `'secret'`、不校验)→ 可伪造任意身份;
- 支付回调跳过签名校验 → 可伪造支付白嫖;
- 全部用 `fs` 读写 JSON 当数据库 → 在 Vercel 只读文件系统上必然失效。

**结论**:该层方向正确(SaaS 必需),但实现是坏脚手架。**SaaS 路线上须按 P0/P3 重建,而非放弃。**

### 2.4 模型现状(ADI)
当前 ADI = 加权酷热复合分(feelsLike 0.40 / dayMax 0.30 / nightMin 0.20 / continuousHeat 0.05 / humidityMuggy 0.05)+ 夜间闷热加分 + 强制升级规则(如夜温≥28 或体感≥37 直接判爆热),分级阈值:爆热≥85 / 热≥75 / 待热≥65 / 一般≥55 / 凉爽≥0。

**作为"酷热指数"它设计精良;作为"销售机会指数"它缺三块**(详见 §4 需求 R-MDL):
1. **无市场维度**:无渗透率、人口体量、购买力 → "ADI Top 城市 ≠ 销售机会 Top 城市";
2. **无基线/异常**:绝对阈值让海口/广州等常态高温城市长期挂"爆热",但那是"正常夏天"非"机会信号";
3. **无闭环校准**:不回流销量,权重/阈值无法验证或调参。

## 3. 目标与非目标

### 3.1 目标
- G1 把单租户看板重构为**多租户 SaaS**:租户隔离的数据、配置、推送、面板。
- G2 让"销售机会分"名副其实:引入**市场权重**与**异常/基线**,产出可解释的排名。
- G3 建立**闭环**:接入租户销量/库存,按租户校准模型——构成续费率与切换成本的护城河。
- G4 重建**真鉴权 + 真计费**,替换 2.3 删除的坏脚手架。

### 3.2 非目标(本期不做)
- 不做实时秒级监控;天气数据 1h 级别刷新足够。
- 不自建天气源;继续基于和风天气。
- 不做竞品/价格抓取(可作为后续集成)。

## 4. 目标用户(租户画像)

| 画像 | 城市范围 | 数据成熟度 | 付费意愿点 |
|---|---|---|---|
| **全国厂商**(美的/格力/海信类) | 全国 ~40+ 城 | 有 ERP/出库数据、有分仓库存 | 闭环校准 + 全国铺货决策 |
| **区域经销商** | 3–10 城 | 数据较零散,可能手工 | 本地精准提醒 + 安装产能调度 |
| **连锁零售商** | 门店所在城市 | 有 POS 销量 | 促销触发时机 |

> 不同画像决定了 P2 闭环数据接入的深度与方式(自动对接 vs 手工录入)。

## 5. 需求

### 5.1 多租户与数据层(P0)
| ID | 需求 | 验收 |
|---|---|---|
| R-T1 | 引入真实多租户数据库(经 marketplace 选型开通,非 mock) | 租户间数据严格隔离,可验证 A 租户读不到 B 租户数据 |
| R-T2 | 租户 / 用户 / 角色 数据模型 | 一个租户多用户,角色:管理员/运营/只读 |
| R-T3 | 真鉴权(签名校验的 JWT 或会话),替换被删假 JWT | token 不可伪造;过期/吊销生效 |
| R-T4 | 所有 API 租户范围化(请求带租户上下文,服务端强制隔离) | 越权请求 403 |

### 5.2 租户配置(P1)
| ID | 需求 | 验收 |
|---|---|---|
| R-CFG1 | 每租户自定义城市集(从平台城市库选取或新增) | 不同租户看板城市不同 |
| R-CFG2 | 每城市可配置市场属性:户数/人口、AC 百户保有量、人均可支配收入 | 字段可编辑、参与打分 |
| R-CFG3 | 每租户可标定模型权重与分级阈值(提供行业默认值) | 改动后该租户排名随之变化 |
| R-CFG4 | 每租户独立推送配置:企微 webhook、推送时刻、触发门槛 | 仅达标时推送,推送记录可查 |

### 5.3 模型增强(P0/P1)
| ID | 需求 | 验收 |
|---|---|---|
| R-MDL1 | **市场加权**:`销售机会分 = f(ADI, 市场增量空间)`(增量空间由渗透率×体量推导) | 饱和高温城市不再长期霸榜 |
| R-MDL2 | **异常/基线**:引入气候态(同期常年值)或分区阈值,用距平替代部分绝对温度 | 常态高温城市仅在异常时高分 |
| R-MDL3 | 分值可解释:展示"市场分 / 异常分 / 热度分"三项构成 | 看板/推送含构成说明 |

### 5.4 闭环与集成(P2,护城河)
| ID | 需求 | 验收 |
|---|---|---|
| R-LOOP1 | 租户销量数据接入:支持手工导入(CSV)与 API 对接(ERP/CRM/POS) | 数据按租户隔离入库 |
| R-LOOP2 | 模型按租户校准:用历史"预测 vs 实际销量"回归调整权重 | 提供校准前后对照与误差指标 |
| R-LOOP3 | 供给侧对照:每城市录入/对接库存与安装档期 | 面板展示"预期需求 vs 可成交 = min(需求, 供给)" |
| R-LOOP4 | 量化建议动作:把机会分换算为"预期增量台数区间"与建议(增调/促销/产能预警) | 每日简报含可执行建议 |

### 5.5 计费与商业化(P3)
| ID | 需求 | 验收 |
|---|---|---|
| R-BILL1 | 真订阅/计费(按租户、城市数、调用量),替换被删坏实现 | 支付回调**强制验签** |
| R-BILL2 | 用量限制与配额 | 超限优雅降级/提示 |

### 5.6 非功能需求
| ID | 需求 |
|---|---|
| R-NF1 | 安全:HSTS/CSP/输入校验;cron 端点必须配 `CRON_SECRET`(当前未配时退化为可伪造头) |
| R-NF2 | 性能:看板首屏天气走缓存(现有 1h);批量城市抓取并发受控(现有 concurrency=6) |
| R-NF3 | 可观测:推送结果、模型校准、数据接入留日志 |
| R-NF4 | 数据合规:销量等租户私有数据不得跨租户泄露,不得用于训练共享模型 |

## 6. 架构方向

### 6.1 共享层 vs 租户层
```
┌─────────────────────────────────────────────┐
│ 平台共享层 │ 和风天气抓取 (qweather.js / api/weather.js)  │
│            │ 企微消息格式化 (wecom-message.js)            │
├─────────────────────────────────────────────┤
│ 租户层      │ 租户配置(城市集/权重/阈值/推送)            │
│            │ 租户数据(销量/库存/安装档期)                │
│            │ 租户范围的面板、API、定时推送                │
│            │ 按租户校准的 ADI 模型                         │
└─────────────────────────────────────────────┘
```

### 6.2 数据模型(草案)
- `tenants`、`users`、`roles`
- `cities_catalog`(平台城市库,lat/lng/province/region/气候分区)
- `tenant_cities`(租户选取的城市 + 市场属性:户数、保有量、收入)
- `tenant_model_config`(权重、阈值、基线来源)
- `tenant_push_config`(webhook、计划、门槛)
- `sales_records`(租户销量,按城市/日期/SKU)
- `supply_records`(库存、安装档期,按城市/日期)
- `push_logs`、`predictions`(留痕,供校准)

> 详细表结构以 P0 阶段的数据库设计稿为准(将更新 `docs/superpowers/specs/*-database-design*`)。

### 6.3 鉴权与隔离
- 真签名 JWT(服务端密钥)或服务端会话;替换假 `verifyJWT`。
- 中间件强制 `tenant_id` 来自鉴权上下文,不接受客户端传入。
- 所有租户表查询带 `WHERE tenant_id = ?` 约束,并以 Postgres **RLS** 作为纵深防御。

### 6.4 数据库与选型(已决,2026-08-06)
**主库:Neon Postgres**(经 Vercel Marketplace 开通,`@neondatabase/serverless` HTTP 驱动)+ **Drizzle ORM**(类型化 schema + 迁移)。

- **选型理由**:数据本质关系型(租户×用户×城市×大区;销量按城市/日期聚合、Top-N、区间扫描、事务),storage 选型矩阵明确映射"Relational data, SQL queries → Neon";Neon 是已下线 `@vercel/postgres` 的继任者,serverless HTTP 驱动天然适配本项目"Vercel Functions + 静态 HTML"架构(无连接池耗尽、按需缩容、适合 pilot);branching 便于 dev/staging/pilot 多环境。
- **租户隔离**:`tenant_id` 列 + 查询强制约束 + Postgres RLS(纵深防御),满足 R-T1/T4。
- **鉴权**:独立真实签名 JWT(如 `jose`),替换被删假 JWT,满足 R-T3。Neon 不锁定未来——若日后需要 Supabase 式 auth,Postgres 数据可平滑迁移。
- **否决备选**:Supabase(Postgres+auth+realtime 一体,但本项目前端为 vanilla JS、非框架 SSR,其 SSR auth helper 假设框架;auth 仅约 50 行可自建)、Mongo Atlas(文档型,关系/聚合/RLS 不如 Postgres)、Turso/Convex(范式不符)、Upstash Redis(KV,非主存)。
- **二级存储(按需,后期)**:Upstash Redis(发送验证码限流、API 配额 R-BILL2、热点缓存);Vercel Blob(仅在需大文件托管时)。
- 注:沙箱网络受限,`vercel integration discover` 实时查询未连通;决策基于 storage 选型矩阵。开通需用户 Vercel 账号(`vercel integration add neon`,P0 启动时执行)。

> **Q1 已确认**:pilot 可提供真实销量/库存数据 → **P0 首版 schema 即包含 `sales_records`/`supply_records`**,P2 闭环走真实数据(pilot 优先 API 自动对接,辅以 CSV 导入),不堆 mock。

## 7. 分阶段路线图

| 阶段 | 范围 | 对应需求 | 交付物 |
|---|---|---|---|
| **P0 地基** | 多租户数据库 + 真鉴权 + 租户隔离数据模型 + 租户配置表 | R-T1~T4 | 可注册/登录、租户隔离的空骨架 |
| **P1 租户化产品 + 模型增强** | 现有看板搬到多租户骨架;市场加权 + 异常基线;租户化推送 | R-CFG1~4、R-MDL1~3 | 每租户独立、排名合理的可用看板 |

> 投资建议前倾到 P2:天气-需求看板本身是商品(易复制、难收费);闭环 + 集成才是续费与切换成本来源。
